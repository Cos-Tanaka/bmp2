# 詳細画面（子課題モーダル）編集機能 設計検討

> ステータス: **検討中（未実装）**
> 対象: 子課題詳細モーダルに「実績工数の日々入力」「進捗率の変更」「チェック状態の変更」を追加する。
> 作成日: 2026-06-19

---

## 1. 背景・目的

現状の BPM2 は Backlog API からデータを取得して表示する **閲覧専用** のダッシュボード。
子課題詳細モーダル（手軽版）も表示のみ。

本検討では、モーダルを **編集可能** に拡張し、以下を画面から直接更新できるようにする。

- 実績工数（`actualHours`）を **日々入力** する
- 進捗率（カスタム属性）を変更する
- チェック状態（カスタム属性）を変更する

---

## 2. 現状構成と制約

| 項目 | 現状 |
|---|---|
| バックエンド | Flask（[backend/app.py](../backend/app.py)）。`GET /api/issues` のみ。読み取り専用。 |
| 永続化 | **なし**。インメモリキャッシュ（`_cache`, TTL=60s）のみ。[docker-compose.yml](../docker-compose.yml) に volume 無し。 |
| 依存 | flask / gunicorn / requests / python-dotenv のみ。 |
| 認証 | 共有の `BACKLOG_API_KEY` 1本。 |
| フロント | [frontend/html/index.html](../frontend/html/index.html) 単一ファイル。詳細モーダルは表示専用。 |

### Backlog API 上の更新可否

| 項目 | 更新可否 | 方法 | 注意点 |
|---|---|---|---|
| 進捗率（子課題カスタム属性） | ✅ | `PATCH /api/v2/issues/{key}` の `customField_{id}` | **リスト型は項目ID**、数値型は数値を送る |
| チェック状態（子課題カスタム属性） | ✅ | 同上 | 同上 |
| 実績工数 `actualHours` | ✅ | `PATCH /api/v2/issues/{key}` の `actualHours` | **累計値の単一フィールド**。日別明細は持てない（後述） |

### 最大の論点：実績工数は「累計値」しか持てない

Backlog の `actualHours` は **単一の累計値** であり、REST API には
**日別の工数明細（ワークログ／タイムシート）を保存・取得する仕組みがない**。
したがって「日々入力」を実現するには、**日別履歴をどこに持つか**を別途決める必要がある。

---

## 3. 実績工数「日々入力」の方式比較

### 方式A：累計加算のみ（DB不要） ★推奨（第一段階）
- モーダルで「本日分 +X.X h」を入力。
- バックエンドが現在の `actualHours` を再取得 → 加算 → `PATCH`。
- 監査用に Backlog コメントへ `6/19 +2.0h（入力者名）` を自動投稿。
- ⭕ 永続化不要・最短。Backlog が唯一の真実。競合に強い（加算直前に再読込）。
- ❌ 日別の内訳・修正・グラフは持てない（コメント文字列が履歴代わり）。

### 方式B：アプリ側に日別台帳（SQLite 追加）
- `(issueKey, 日付, 工数, 入力者)` を SQLite に保存。
- `actualHours = 台帳の合計` を Backlog に書き戻す。
- ⭕ 日別入力・修正・カレンダー・バーンダウンが作れる。
- ❌ DB＋volume 追加。台帳⇄Backlog の整合性設計が必要（二重管理）。

### 方式C：コメントを台帳化（DB不要）
- 日々の入力を所定フォーマットのコメントで記録し、合計を `actualHours` に反映。
- ⭕ DB不要で日別履歴も残る。
- ❌ コメント解析が脆い・手動コメントと混在。**非推奨**。

### 推奨ロードマップ
**まず方式A** で導入 → 日別の内訳・グラフが必要になった段階で **方式B** へ拡張。

---

## 4. 進捗率・チェック状態の更新設計（共通）

- リスト型カスタム属性は **テキストではなく項目ID** で更新する必要があるため、
  バックエンドに **選択肢一覧（ID＋名称）を返す API** を追加する。
  （`GET /projects/{key}/customFields` の `items` を整形して返す）
- 現状フロントは表示用テキストしか保持していないため、モーダルでは
  選択肢付きプルダウンに置き換える。
- 数値型の進捗率の場合は数値入力欄、リスト型ならプルダウン、と型に応じて出し分ける。

---

## 5. 追加バックエンドAPI（案）

| メソッド | パス | 役割 |
|---|---|---|
| `GET` | `/api/issue/<key>` | モーダル表示用に1課題の最新値を取得（書込前後の整合用） |
| `GET` | `/api/field-options` | 進捗率・チェック状態の選択肢（ID＋名称＋型）を返す |
| `PATCH` | `/api/issue/<key>` | `actualHours`（加算 or 設定）／進捗率／チェック状態 を更新 |

### 共通の実装ポイント
- 既存ヘルパー `backlog_get()` に加え、`backlog_patch()` / `backlog_post()`（コメント投稿用）を追加。
- 書き込み成功後は `_cache.pop("issues", None)` でキャッシュ破棄 → ダッシュボードへ即反映。
- Backlog の更新APIは `Content-Type: application/x-www-form-urlencoded` でパラメータ送信。

### PATCH リクエスト例（方式A・進捗率/チェック状態同時更新）
```
PATCH /api/issue/PROJ-123
{
  "addActualHours": 2.0,        // 累計に加算する本日分
  "progress": 60,               // 数値型の場合
  "checkStatusItemId": 4521     // リスト型カスタム属性の項目ID
}
```
→ バックエンドで現値再取得 → actualHours 加算 → customField_* 反映 → Backlog PATCH → コメント投稿 → キャッシュ破棄。

## 6. フロント（モーダル）UI 案

詳細モーダルを「閲覧専用」→「編集可能」に拡張する（[index.html](../frontend/html/index.html) の `openChildModal`）。

- **実績工数**: 「本日分」入力欄 ＋ [記録] ボタン（方式Aは累計へ加算）。現在累計も併記。
- **進捗率**: 型に応じてプルダウン or 数値入力。
- **チェック状態**: 選択肢プルダウン。
- **[保存]** → `PATCH /api/issue/<key>` → 成功でモーダル値更新 ＆ 背景テーブルを `fetchData(true)` で再取得。
- 保存中はスピナー／二重送信防止、失敗時はエラー表示。

## 7. 運用・非機能上の注意

1. **入力者の記録**: APIキーは共有1本のため、すべての更新が「キー所有者」名義になる。
   「誰が入力したか」を残すなら、方式Aのコメントに入力者名を埋める／将来的に人別APIキーやOAuthを検討。
2. **書き込み権限**: 現 `BACKLOG_API_KEY` に課題更新・コメント投稿の権限があるか要確認。
3. **同時編集の競合**: 取得→加算→PATCH の間で競合し得る。実績工数は「加算方式」にすると堅牢。
   進捗率・チェック状態は「最後の保存が勝つ」想定（必要なら更新前確認ダイアログ）。
4. **入力値バリデーション**: 工数は 0 以上の数値、進捗率は 0–100、など。
