# 改修計画書：ガントチャート 案件別ビューを優先度・優先順位順に並べる

- 作成日: 2026-10-28
- 対象: `backend/app.py`（親課題レスポンスへの項目追加）、`frontend/html/gantt.html`（案件別ビューの並び替え）
- ステータス: **確定版**（2026-10-28 `docs/質問票_ガント案件別_優先度順表示.md` の回答を反映。Q1〜Q9 すべて推奨案を採用）

## 1. 背景・目的

| 要望 | 目的 |
|---|---|
| ガントの「📋 案件別」ビューで、親案件を Backlog の**優先度**（高・中・低）と**優先順位**（数値）の順に並べる | 優先して進めるべき案件を上から順に把握できるようにする |
| 優先順位が空欄の案件は **Kintone番号の若い順 → Backlog 登録日の若い順** に並べる | 優先順位を付けていない案件も、受付順に近い安定した順序で並ぶようにする |

## 2. 現状

- 案件別ビューの行は `visibleRows()`（[gantt.html:650](frontend/html/gantt.html:650)）が `allData` を**フィルタするだけで並べ替えていない**。つまり順序は `/api/issues` の返却順＝ Backlog `/issues` API の既定順（実質「登録日の新しい順」）のまま。
- `/api/issues` の親課題（`build_response`、[app.py:559](backend/app.py:559)）には、並び替えに必要な項目が**含まれていない**。

| 必要な情報 | Backlog 上の所在 | 現在のレスポンス |
|---|---|---|
| 優先度 | 標準項目 `priority`（`{id, name}`。id 2=高 / 3=中 / 4=低） | 無し |
| 優先順位 | カスタム属性「優先順位」（id 717648、**数値型** typeId 3） | 無し |
| Kintone番号 | カスタム属性「Kintone番号」（id 16751、**文字列型** typeId 1） | リンク URL（`kintoneUrl`）のみ。番号そのものは無し |
| 登録日 | 標準項目 `created`（ISO 8601、UTC） | 無し |

→ **バックエンドの改修（項目追加）とコンテナ再ビルドが必要**。

## 3. 実データ調査（2026-10-28 時点、親課題 105 件）

| 項目 | 結果 | 計画への影響 |
|---|---|---|
| 優先度 | 高 20 件 / 中 85 件 / 低 0 件 | 標準項目のため空欄は無い（必須項目） |
| 優先順位 | 入力あり **7 件のみ**（すべて優先度「高」）。値は 1, 2, 3, 4, 5, 6, **30** | 重複は現状無し。30 は飛び番（Q4） |
| Kintone番号 | `s-NNNN` 形式 100 件 / `help-15825` 1 件 / 空欄 4 件 | 形式の違う番号・空欄の扱いを決める必要あり（Q2） |
| Kintone番号の重複 | `s-1479`（V2A9-2417 / V2A9-1588）、`s-1506` など同一番号の案件が複数ある | 同番号の並びは登録日で決まる |

## 4. 並び順の定義

親案件を次のキーで**上から順に**比較する。

| 順 | キー | 並び | 欠損時 |
|---|---|---|---|
| 1 | 優先度 | 高 → 中 → 低 | （発生しないが）中扱い |
| 2 | 優先順位 | 数値の**小さい順** | 空欄は**同じ優先度の中で末尾**（Q1。中(1) は 高(空欄) より下） |
| 3 | Kintone番号 | `s-` の番号を**数値部分**の小さい順（`s-1479` < `s-1515`。文字列比較だと桁数違いで崩れるため数値比較） → `help-` など `s-` 以外の形式（その中で数値順） → 空欄（Q2） | — |
| 4 | Backlog 登録日 | 古い順（「若い順」＝日付の小さい順。Q3） | — |
| 5 | 課題キー | 番号順 | 最終タイブレーク（表示を毎回同じ順に固定するため） |

- キー 3・4 は「優先順位が空欄の案件どうし」の並びを決めるためのもの。優先順位が入っている案件どうしで値が同じ場合も、同じ規則で並べる（Q4）。
- 優先順位 30（V2A9-2467）は値どおり 6 の次に並べる。入力誤りなら Backlog 側で修正する（Q4）。
- 子課題の並び（`sortChildren` ＝ 一覧画面と共通の `childSort` 設定）は**変更しない**。

## 5. 改修方針

### 5.1 バックエンド（`backend/app.py`）

- `_fetch_raw()` で「優先順位」カスタム属性の ID を引き、`field_ids` タプルの**末尾**に `rank_field_id` を追加する。フィールド名は既存と同様に環境変数で上書き可能にする（`RANK_FIELD_NAME`、既定 `優先順位`）。
  - `field_ids` は `build_response(*field_ids)` にそのまま展開される設計（[app.py:114](backend/app.py:114)）なので、`build_response` の引数を 1 つ足すだけで局所更新経路（`_raw`）にも自動的に反映される。
- `build_response()` の親課題 dict に以下を追加する（子課題には追加しない）。

| キー | 値 | 例 |
|---|---|---|
| `priority` | 優先度名 | `"高"` |
| `priorityId` | 優先度 ID（並び替えはこちらで行う。名称変更に強い） | `2` |
| `rank` | 優先順位（数値。空欄は `null`） | `3` |
| `kintoneNo` | Kintone番号の生の文字列（空欄は `null`） | `"s-1479"` |
| `created` | 登録日時（Backlog の値そのまま） | `"2026-10-05T04:21:29Z"` |

- **並び替え自体はフロントエンドで行う**（Q5）。バックエンドは素材を渡すだけにし、一覧画面など他画面の順序には影響させない。
- `.env.example` / CLAUDE.md の環境変数表に `RANK_FIELD_NAME` を追記する。

### 5.2 フロントエンド（`frontend/html/gantt.html`）

- 比較関数 `compareParentsByPriority(a, b)` を追加し、`visibleRows()` の最後で `sort` する。4 章のキーをそのまま実装する。
  - Kintone番号は `kintoneNo` から数値部分を抽出して数値比較し、`s-` 以外の形式・空欄を後ろへ回す（Q2）。
  - `priorityId` 等が無い古いスナップショット（5.3）でも例外にならないようフォールバックする（欠損値は末尾扱い＋課題キー順）。
- 「全て展開／折りたたみ」・担当者フィルタ時の自動展開・横スクロール位置の保持など既存の挙動は、行の順序が変わるだけなので影響なし。
- 担当者別ビュー（`visibleAssigneeGroups()`）の案件順は**変更しない**（Q6）。
- 並び順の切り替え UI は設けない（Q8）。
- **優先度バッジ**（Q7）: 親案件行の健全性アイコンの右に小さなバッジを出す。
  - 「高」は赤系、「低」は灰色、「中」は控えめな黄系。優先順位があれば番号を併記（例: `高1`）。
  - 「中」で優先順位が無い案件（大多数）はバッジを出さない（85 行に同じバッジが並ぶだけで情報にならず、件名の幅を削るため）。
  - バーのツールチップに「優先度」（優先順位があれば併記）と「Kintone番号」を追加する。

### 5.3 反映・運用上の注意

- バックエンド変更のため `docker compose up -d --build` が必要（この環境では 2〜3 分）。
- 再起動直後はディスク上の旧スナップショット（新項目なし）が返るため、**最初のバックグラウンド更新（約 20 秒）が終わるまでは並びが現行のまま**になる。5.2 のフォールバックで画面は壊れない。
- Backlog 側で優先度・優先順位を変更した場合、ガントへの反映は次回のスナップショット更新時（`CACHE_TTL` 既定 60 秒以内）。BPM から親課題は編集しないため、局所更新経路での考慮は不要。
