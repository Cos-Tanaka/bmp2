# 実績工数入力の省力化 設計検討

> ステータス: **検討中（未実装）**
> 対象: 作業者が「1日に複数タスク分の実績工数」を登録するのにかかる時間を削る。
> 作成日: 2026-07-31

---

## 1. 現状のフローと、時間がかかっている箇所

現在、実績工数を1件登録するまでの手順は以下（[index.html](../frontend/html/index.html) / [gantt.html](../frontend/html/gantt.html) 共通）。

1. ダッシュボードを開く
2. 対象の**親案件を探す** → 展開 → **子課題を探す**
3. 実績工数セル（または子課題タイトル）をクリックしてモーダルを開く
4. 「追加工数」「名前」「日時」を入力して［追加］
5. 保存完了を待つ
6. **1〜5 をタスクの数だけ繰り返す**

1日に N タスク実施していれば、この一式が N 回発生する。コスト構造を分解すると次の3つ。

| # | コスト | 内訳 | 1件あたりの体感 |
|---|---|---|---|
| C1 | **探す** | 親案件を思い出す→展開→子課題を探す。担当者別ガントを使っても、モーダルは1課題ずつしか開けない | 20〜40秒 |
| C2 | **入力する** | 工数・名前・日時。名前は `localStorage` から復元されるが、日時は毎回、工数はキーボード入力 | 10〜20秒 |
| C3 | **待つ** | 保存が**同期的に重い**（下記） | **1件あたり十数秒〜20秒** |

### C3 は実装上のボトルネックで、いちばん確実に削れる

[backend/app.py](../backend/app.py) の `api_worklog_add()` は、1件の登録ごとに次を**同期**で実行している。

```
POST /api/worklog/<key>
  → backlog_get(/issues/<key>)      … 現在の actualHours 取得
  → backlog_patch(/issues/<key>)    … 加算した合計を書き戻し
  → add_worklog(...)                … SQLite に履歴を INSERT
  → refresh_snapshot()              … ★ Backlog 全件再取得（コメント記載どおり 1 回 ~20 秒）
```

`refresh_snapshot()` は「全課題の再取得」であり、コード上のコメントでも `~20 秒` とされている処理。
これを**1件登録するたびに、レスポンスを返す前に**回している。さらにフロント側は完了後に
`onDataChanged()` → `fetchData(true)` も走らせる。

つまり **5タスク入力すると、待ち時間だけで合計 100 秒前後**になる。
削除（`api_worklog_delete`）も同じ構造。ここは機能を変えずに削れる純粋な無駄。

### そのほか現状の制約

| 項目 | 現状 | 影響 |
|---|---|---|
| 入力者 | `worklog.name` は**自由文字列**。Backlog ユーザーと紐付いていない | 表記ゆれが起きる。「自分の担当課題だけ出す」ができない |
| 入力単位 | 1リクエスト = 1課題 | まとめ入力の口がない |
| 一覧画面 | [worklog.html](../frontend/html/worklog.html) は**検索専用**（入力できない） | 「今日の入力状況を見ながら埋める」ができない |
| 日時 | `datetime-local` で分まで入力 | 実績工数の集計は**日単位**（`/api/worklog/search` は `date(added_at)` で GROUP BY）なので、分の精度は使われていない |

## 2. 打ち手の候補

削るべきコストが C1 / C2 / C3 と分かれているので、打ち手も対応させて整理する。

### 打ち手A：保存を軽くする（C3）★最優先・機能変更なし

**A-1. `refresh_snapshot()` を同期実行しない**
登録処理のレスポンスは Backlog への `PATCH` と SQLite INSERT が終わった時点で返し、
スナップショット更新はバックグラウンドスレッドに投げる（`_refresh_lock` があるので多重実行は既に防げている）。
レスポンスには更新後の `actualHours` を既に含んでいるので、フロントはその値でモーダルの
実績/差分/残工数を即時更新すればよい（`refreshChildModalHours()` の入力元をレスポンスに変えるだけ）。

- ⭕ **1件あたり ~20 秒 → 1〜2 秒**。既存モーダルのままでも効く
- ⭕ 変更範囲が小さい（バックエンド数行＋フロント数行）
- ❌ 直後のダッシュボード再描画は最大 `CACHE_TTL` 秒ぶん古いままになり得る → 楽観更新でカバーする

**A-2. 変更した課題だけスナップショットを差し替える（A-1 の代替／併用）**
全件取得ではなく、当該子課題の値だけスナップショット内で書き換え、親の集計と `health` を再計算する。

- ⭕ 全件取得が消えるので正確さも速さも両立
- ❌ `calc_health` / 親集計のロジックが「全件ビルド」と「部分更新」の2箇所に増える（保守の重複）
- → **まず A-1。整合性が問題になったら A-2 を検討**、が費用対効果は良い

### 打ち手B：まとめて入力する画面をつくる（C1 + C2）★本命

新規ページ `mytime.html`（仮称・「今日の実績」）。**1画面・1回の保存で1日分を終わらせる**のが狙い。

```
┌ 今日の実績 ─────────────────────────────────┐
│ 入力者 [田中 ▼]        対象日 [2026-07-31]  ← ページで1回だけ選ぶ
├─────────────────────────────────────────────┤
│ ASPIT-120 会員基盤     ASPIT-133 API改修  [ 2.0 ]h  [+0.5][+1]
│ ASPIT-120 会員基盤     ASPIT-140 結合試験  [ 3.5 ]h  [+0.5][+1]
│ ASPIT-98  受発注       ASPIT-101 打合せ    [ 1.0 ]h  [+0.5][+1]
│ ＋ 課題を追加（インクリメンタル検索）
├─────────────────────────────────────────────┤
│ 合計 6.5h  （所定 8.0h との差 -1.5h）      [ まとめて保存 ]
└─────────────────────────────────────────────┘
```

設計のポイント:

- **入力者と日付は画面で1回だけ**指定（`localStorage` に保持）。行ごとの再入力を廃止する
- **行の初期候補**を自動で並べる。ここが C1 を消す肝:
  1. その日すでに入力済みの行（編集可能な状態で表示）
  2. 直近7日で自分が入力した子課題（＝「毎日触っているタスク」はほぼここに出る）
  3. 自分が担当者の未完了子課題
  4. それ以外は検索で追加
- 工数欄は **0.25 刻み＋クイックボタン**、Enter で次行へ（テンキーだけで完結）
- 合計 h と所定時間との差分を常時表示 → **入力漏れがその場で分かる**
- 保存は**1リクエスト**（打ち手C）

これで N タスクでも「開く → 数字を N 個打つ → 保存1回」に収まる。

**B-2. 「昨日をコピー」ボタン**
前営業日の入力内容を行ごと複製して数字だけ直す。1日で複数タスクを回す人は日々の顔ぶれが似るため、実測入力の大半がこれで済む可能性が高い。

**B-3. 割合配分モード（オプション）**
「今日の稼働 7.5h」を先に入れ、各行にスライダー／% で配分して h を自動計算する。
「厳密な時間は覚えていないが、だいたい半々」という実態に合い、思い出すコスト自体を下げる。

### 打ち手C：まとめ保存 API

```
POST /api/worklog/bulk
{
  "date": "2026-07-31",
  "userId": 12345,            // 打ち手D
  "name": "田中",
  "entries": [
    { "childKey": "ASPIT-133", "hours": 2.0, "parentKey": "ASPIT-120", "parentTitle": "会員基盤" },
    { "childKey": "ASPIT-140", "hours": 3.5, ... }
  ]
}
→ { "ok": true, "results": [ { "childKey": "...", "actualHours": 12.5 }, ... ] }
```

- 同一課題への複数行は**合算してから `PATCH` 1回**
- `refresh_snapshot()` は**全件終わってから1回だけ**（打ち手A-1 と組み合わせるなら非同期で1回）
- 部分失敗は行単位で結果を返し、画面で失敗行だけ赤くして再送できるようにする
- **上書きセマンティクス**が必要: 「その日・その課題・その人」の入力を**置き換える**か**加算する**か。
  まとめ入力画面は「今日の合計を書く」画面なので**置き換え**が自然。
  既存の日次入力行を論理削除 → 新規 INSERT → 差分を `actualHours` に反映、という実装になる（要決定・§4）

### 打ち手D：入力者を Backlog ユーザーに紐付ける

`worklog` テーブルに `user_id INTEGER` を追加し、`/api/project-users` の id を保存する
（`name` は表示用に残す＝既存データと互換）。

- 打ち手B の「自分の担当課題」「自分の直近の入力」の抽出が可能になる（これが無いと B の候補提示が作れない）
- 表記ゆれ（「田中」「田中太郎」「tanaka」）が消え、[worklog.html](../frontend/html/worklog.html) の集計精度が上がる
- 既存データは `name → user_id` の対応表を一度作って移行、対応が付かないものは `NULL` のまま

### 打ち手E：入力漏れを翌日に気づける仕組み

実は「後日まとめて思い出す」時間が実入力より大きいことが多い。
[worklog.html](../frontend/html/worklog.html) に **日別・人別の合計 h カレンダー**を足し、
0h または所定時間に満たない日をハイライトする。当日中に埋まれば思い出しコストがゼロになる。

### 打ち手F：タイマー方式（開始／終了ボタン）— 今回は**非推奨**

「作業開始」「終了」を押して自動計測する案。理屈上は入力ゼロになるが、

- 押し忘れ・押しっぱなしの補正作業が発生し、かえって手間が増える
- 会議や割り込みが多い働き方では実態と乖離する
- 常時開いている画面が前提になる

現実的な折衷は「前回入力からの経過時間をデフォルト値として**提案**する」程度に留めること。

## 3. 推奨ロードマップ

| フェーズ | 内容 | 効く箇所 | 規模感 |
|---|---|---|---|
| **Phase 1** | 打ち手A-1（保存の非同期化＋レスポンス値での楽観更新） | C3 | 小（バックエンド／フロント各数行） |
| **Phase 2** | 打ち手D（`user_id` 追加）＋ 打ち手C（`/api/worklog/bulk`） | 基盤 | 中 |
| **Phase 3** | 打ち手B（`mytime.html` まとめ入力画面）＋ B-2「昨日をコピー」 | C1・C2 | 中〜大 |
| **Phase 4** | 打ち手E（入力状況の可視化）／ 必要なら B-3（割合配分） | 思い出しコスト | 小〜中 |

**Phase 1 だけでも体感は大きく変わる**（1件20秒待ちが消える）ので、まずここを単独でリリースし、
まとめ入力画面は Phase 2 以降で腰を据えて作るのが安全。
