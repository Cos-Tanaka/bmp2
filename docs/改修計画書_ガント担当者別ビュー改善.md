## 1. 背景・目的

| # | 要望 | 目的 |
|---|---|---|
| 2 | 担当者の行に、紐付くスケジュールの帯を**1 本**で表示する | 「▶ 全て閉じる」で担当者行だけを並べたとき、**全担当者の空き（帯が無い期間）を一覧で確認したい** |
| 3 | 担当者の次の行に**親案件の行**を出し、その下に子課題をぶら下げる（開閉制御付き） | 「▼ 全て開く」時、1 人が複数案件を持つと、同名の子課題（例「詳細設計」）がどの案件のものか分からない |

要望 2 と 3 は**同じ画面の同じ行構造**を触るため、1 つの改修としてまとめて設計します。

## 2. 現状の担当者別ビュー

```
👤 山田太郎  [5]  計 40h/32h          ← グループ行（バーは無し＝トラックが空）
    ASPIT-123 [ASPIT-100] 詳細設計    ▬▬▬▬
    ASPIT-145 [ASPIT-102] 詳細設計       ▬▬▬
👤 未割当 …
```

- 行は **担当者グループ行 → 子課題行** の 2 階層のみ（[gantt.html:846 `renderAssigneeGantt`](frontend/html/gantt.html:846)）。
- グループ行のトラックは `<div class="gtrack">` が空で、**バーが一切描かれない**（[gantt.html:901](frontend/html/gantt.html:901)）。閉じると「その担当者に何がいつあるか」は完全に見えなくなる ← 要望 2 の対象。
- 子課題行は親案件を `[ASPIT-100]` の**キーだけ**併記（案件名は出さない）。同名子課題が並ぶと判別しづらい ← 要望 3 の対象。
- グループの開閉は `collapsedGroups`（`'a:' + assigneeId` の Set、既定=全開）。「全て開く／閉じる」は `setAllExpanded()` がこの Set を空にする／全キーで埋める（[gantt.html:975](frontend/html/gantt.html:975)）。

## 3. 改修方針

### 3.1 行構造（要望 3）

担当者グループ行と子課題行の間に**親案件行**を挟み、3 階層にします。

```
👤 山田太郎  2案件 / 5課題  計 40h/32h    ▬▬▬▬▬▬   ▬▬▬▬     ← 集約帯（要望 2）
   ▼ ASPIT-100 受注管理システム改修  [3]   ▬▬▬▬▬▬            ← 親案件行（担当者ぶんの集約帯）
        ASPIT-123 詳細設計                 ▬▬▬▬
        ASPIT-131 単体テスト                    ▬▬▬
   ▶ ASPIT-102 在庫マスタ移行  [2]                    ▬▬▬▬   ← 折りたたみ中
👤 未割当 …
```

- **データ構造**: `visibleAssigneeGroups()` の戻り値を `g.children`（フラット配列）から `g.projects = [{ parent, children }]` へ拡張する。`g.children` はフラット参照として残し、集約帯・件数・工数合計の計算に使う（`buildAxis` への供給も現行のまま維持できる）。
- **親案件行の内容**: 開閉トグル / 案件キー（Backlog リンク）/ 案件名 / その担当者ぶんの課題件数バッジ / 集約帯。
- **開閉キー**: 既存の `collapsedGroups` に `'ap:' + assigneeId + ':' + parentId` 形式で親案件行のキーも格納する（同じ案件が複数担当者にぶら下がるため、担当者 ID を含めて一意化する）。既定は**開**（＝閉じたものだけ記録する現行方式を踏襲）。
- **「全て開く／閉じる」**（Q8 で確定）: 「▶ 全て閉じる」＝担当者行のみ（親案件行も畳む＝空き確認の状態）、「▼ 全て開く」＝全 3 階層を展開。中間段階の「案件まで開く」チップは**追加しない**。
- **インデント**: 担当者 8px / 親案件 26px / 子課題 46px。改修要望 1（左ペイン 520px）を前提とするため、子課題の件名幅は現行より広く保てる。
- **子課題行の `[親キー]` 併記**: 親案件行が出るため冗長になるので**削除する**（Q9 で確定。そのぶん件名に幅を回す）。
- **並び順**（Q10 で確定）:
  - 担当者内の案件: 「その担当者の子課題の最早開始日」昇順（同日は案件キー順）。**その担当者の子課題がすべて日付未設定で期間を引けない案件は、グループ内の最下部に案件キー順**で並べる。
  - 案件内の子課題: 開始日昇順（同日は課題キー順）。**開始日が未設定の子課題は案件内の最下部に課題キー順**で並べる。
  - ※ 既定 ON の「日付なしを隠す」では、これらの行はそもそも表示されない。チップを OFF にしたときの並び順を上記で規定する。
- **担当者行の件数表示**: 現行 `[5]` → `2案件 / 5課題` に変更。

### 3.2 集約帯（要望 2）

担当者行・親案件行のトラックに、**配下の子課題の期間を 1 レーンにまとめた帯**を描きます。

- **「1 本」の解釈**（Q1 で確定）: **1 レーン（1 行ぶんの高さ）に、実作業のある期間だけを塗り、間は空ける**（＝A 案）。最早開始〜最遅期限を 1 本の連続バーで塗る方式は不採用（案件の谷間＝空きが塗り潰され、目的を達成できないため）。
- **セグメント生成**（新関数 `mergeSegments(children)`）:
  ```js
  // 子課題の期間を開始日昇順に並べ、重なり／連続をまとめる
  for (const r of sortedRanges) {
    const last = segs[segs.length - 1];
    if (last && r.start <= nextBusinessDay(last.due)) {   // 連結判定（Q2）
      last.due = max(last.due, r.due); last.items.push(r.item);
    } else segs.push({ start: r.start, due: r.due, items: [r.item] });
  }
  ```
  - **連結判定**（Q2 で確定）: 「前の期限日の翌**営業日**までに次が始まるなら連結」（間が土日だけなら空きと見なさない）。祝日は Backlog から取得できないため考慮しない（祝日は隙間として現れる）。
- **色**（Q3 で確定）: セグメントに含まれる子課題の**最も悪い健全性**（🔴 > 🟡 > 🟢）を採用。進捗の塗り分けは行わない（複数課題の平均は解釈が難しいため）。
- **表示タイミング**（Q5 で確定）: 開いているときも閉じているときも**常に表示**（親案件行も同様）。
- **日付未設定の子課題**: 帯には現れない（`resolveRange` が引けないため）。既定 ON の「日付なしを隠す」では行自体も非表示。
- **ツールチップ**: 既存の `showTip(ev, id)` は課題 ID 前提のため、帯用に `showBandTip(ev, key, segIndex)` を追加する。内容は 担当者（または案件）／期間（`8/3 → 8/21（19日）`）／**同時稼働の最大件数**／含まれる課題（開始日順に最大 5 件＋「ほか N 件」）／予定・実績工数の合計。
- **クリック**: 帯はクリックしても課題を特定できないため、**クリック無効**（開閉はトグルまたは行の左ペイン側で行う）。子課題行のバーは従来どおり Backlog を開く。
- **描画**: 既存 `.gbar` とは別クラス `.gband` を新設する。既存のバー描画・健全性判定・軸モデルには手を入れない。

#### 3.2.1 並列タスクの見せ方（Q4 の追加指示を反映）

回答で「**並列タスクが常態化しているので見やすく**」との指示があったため、単に「重なりを濃くする」だけでは不十分と判断し、**同時件数を高さ＋濃度の 2 要素で表現する**方式に確定します（濃淡だけだと、常時 2〜3 件が走る現場では帯の大半が同じ濃さになり差が読めないため）。

- **区間の算出**: セグメント内の全課題の開始日・期限翌日を境界にしたスイープで、`{ from, to, n（同時件数）}` の**サブ区間**に分割する（`O(n log n)`）。
- **高さ**（同一行内で下端を揃えて描くため、山の形が同時件数のミニ棒グラフとして読める）:

  | 同時件数 | 高さ | 塗りの不透明度 |
  |---|---|---|
  | 1 件 | 6px | .45 |
  | 2 件 | 10px | .65 |
  | 3 件以上 | 14px | .85 |

- **件数ラベル**: サブ区間の幅が 14px 以上なら、区間中央に件数の数字を重ねる（`2` / `3` / `4`…）。幅が足りない区間はラベルなし（ツールチップで確認）。
- **色**: サブ区間ごとに、その区間で走っている課題の最も悪い健全性で塗る（区間単位なので「赤い課題が走っている期間」が正確に分かる）。
- **行の高さ**: 担当者行・親案件行は現行 34px のため、最大 14px の帯は余白内に収まる（変更不要）。
- **凡例**: 画面右上の凡例に「帯の高さ＝同時に走っている課題数」の 1 項目を追加する。

### 3.3 空きの見せ方（要望 2 の目的）

「▶ 全て閉じる」を押すと**担当者行だけが縦に並び、各行に帯が 1 レーン**になります。帯が無い横位置＝その担当者の空き、として目視できます。

- 空き期間そのものを塗る／ハイライトする処理は行いません（Q6 で確定）。
- 「今日以降の空き」を強調したい場合は、既存の今日線（`.gtoday`）が縦に通っているため、今日線より右で帯が途切れている担当者を探す運用になります。

### 3.4 案件別ビュー（📋）への影響

**変更しません**（Q12 で確定）。案件別ビューの親行には既に「子課題から集約した細バー（`.gbar.rolled`、最早開始〜最遅期限の 1 本）」があり、こちらは案件の期間を示すという別の意味を持つためです。

**実装順序: 要望 1 →（本書）要望 3 → 要望 2 の順で実装し、3 つまとめて 1 回でリリース**（Q13 で確定）。
理由: 3 階層化でインデントが 1 段深くなるため幅拡張（要望 1）が前提になり、また集約帯（要望 2）は担当者行と親案件行の**両方**に描くため、行構造を先に確定させたほうが手戻りが無いためです。

## 5. 影響範囲・リスク

- **バックエンド・API 変更なし**。リリースは `docker compose restart frontend` のみ。
- **案件別ビュー・index.html への影響なし**。共有する `bpm2-filter` は触らない。localStorage キーの追加も無し（開閉状態は現行同様メモリ保持）。
- **行数の増加**: 親案件行が「担当者 × 案件」の組合せぶん増える。全開時の行数は現行 +（数十〜百）程度を想定。現行の `innerHTML` 一括生成で問題になる規模ではないが、実データで描画時間を確認する。
- **軸のブレなし**: `buildAxis` には従来どおりフラットな子課題集合を渡すため、開閉しても軸範囲は変わらない（現行仕様の維持）。
- **帯の誤読リスク**: セグメントを繋げる／切る判定（Q2: 土日は連結）次第で「空きに見える／見えない」が変わる。ツールチップに期間を出して裏取りできるようにする。祝日は連結されず隙間になる点をガイドに明記する。
- **並列タスクの表現の限界**: 1 レーンに畳む以上、同時件数は高さ・濃度・数字ラベルでしか表現できず、「どの課題が重なっているか」までは帯だけでは分からない。厳密に見たい場合は担当者行を開いて子課題行で確認する運用とする（ツールチップには課題名を最大 5 件出す）。
- **同時件数が多い現場での見え方**: 3 件以上を同一の高さ・濃度に丸めるため、5 件と 10 件の区別は付かない。数字ラベルで補完する（幅が足りない区間はツールチップ）。運用してみて「4 段階目が欲しい」等あれば閾値の調整で対応可能（CSS とテーブル値の変更のみ）。
- **フィルタとの整合**: 帯は「フィルタ通過後の子課題」だけを集約する。したがって「完了を隠す」ON では完了済みタスクが空きに見える。これは意図どおり（現在〜将来の負荷を見る）だが、ガイドに明記する。

## 6. テスト計画（手動）

1. 「▶ 全て閉じる」で担当者行だけが並び、各行に帯が 1 レーンで出ること。帯の無い担当者・期間が空きとして識別できること。
2. 帯の期間が、その担当者の子課題の期間の和集合と一致すること（数件を手計算で照合）。
3. 週末をまたぐ連続タスク（金曜期限 → 月曜開始）が**連結**され、平日 3 日以上空くケースは**分断**されること。
4. 期間が重なる 2 件・3 件以上を持つ担当者で、重なり区間の**高さと濃度が段階的に変わり**、幅のある区間には件数の数字が出ること。ツールチップに「同時 N 件」と課題名が出ること。
4-2. 並列が常態の担当者（常時 2〜3 件）で、帯が一様な塊に見えず山の形（同時件数の増減）が読めること。凡例に「帯の高さ＝同時課題数」が出ていること。
5. 「▼ 全て開く」で 担当者 → 親案件 → 子課題 の 3 階層が出ること。同名子課題がどの案件のものか判別できること。
6. 親案件行の個別トグルで、その案件の子課題だけが開閉すること。他の担当者にぶら下がる同じ案件の開閉状態と独立していること。
7. 60 秒ポーリング再描画・フィルタ変更後も、開閉状態とスクロール位置が保持されること。
8. 各フィルタ（健全性 / 状態 / 完了を隠す / カスタムステータス / 日付なしを隠す / 担当者複数選択）適用時に、帯・件数・親案件行が連動すること。
9. 粒度 日／週／月それぞれで帯の位置とセグメントの切れ目が正しいこと（月粒度は日割り按分）。
10. 子課題の件名クリックで詳細モーダルが開くこと（帯・親案件行のクリックで誤って開かないこと）。
11. 案件別ビューが従来と完全に同一であること（回帰）。
12. ライト／ダークテーマ両方で、帯の 3 段階の濃度差と数字ラベルが判別できること。
13. 「日付なしを隠す」を OFF にしたとき、期間の引けない案件・子課題がそれぞれの階層の最下部に**案件キー／課題キー順**で並ぶこと。
